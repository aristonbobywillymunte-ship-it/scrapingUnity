## 1. Executive Summary
This document defines the final technical contract and internal architecture for the Python scraping/data plane of the Social Media Scraping API. The Python workers function as an independent, modular execution environment responsible for performing the actual extraction of social media data, guided by execution instructions (jobs) originating from the Laravel control plane. The architecture is HTTP-first, utilizing conservative browser fallback only when necessary, and strictly separates scraping execution from customer billing, API serving, and tenant isolation, which remain securely managed by Laravel.

## 2. Scope
- Architecture and module boundaries of the Python scraping workers.
- The contract between Laravel (Control Plane) and Python (Data Plane).
- Internal execution flow, including HTTP fetching, parsing, normalizing, and proxy selection.
- Error classification, stop conditions, and retry strategies.
- Observability, logging, and security boundaries within the Python environment.

## 3. Non-Goals
This specification does **not** include:
- Laravel application code, API routes, or migrations.
- Actual Python implementation code or scripts.
- Infrastructure deployment files (e.g., Dockerfiles, docker-compose).
- Platform-specific scraping logic, bypass implementations, or reverse-engineered platform APIs.
- User Interface (UI) design or runtime code.

## 4. Architectural Role of Python
Python acts exclusively as the **Scraping / Data Plane**. It executes `scrape_executions` generated by the control plane, acquires the necessary network resources (proxies), fetches raw data, parses the response, normalizes it into a universal schema, and persists the result to PostgreSQL. Python does not manage customer API keys, webhook deliveries, billing/quota, or tenant isolation.

## 5. Runtime Topology
The Python environment runs as independent worker containers (managed via Docker Compose) orchestrated by Redis queues.
- **PostgreSQL:** Durable Source of Truth for jobs, executions, and normalized items.
- **Redis:** Used exclusively for transient coordination (queues, locks, cooldowns, worker heartbeats, circuit breaker state).
- **Control Plane Interaction:** Python receives jobs from Redis and writes structured results directly to PostgreSQL using a defined data-access contract. No direct HTTP callbacks to Laravel are required for basic job completion, though shared state exists via Redis/PostgreSQL.

## 6. Python Package / Module Boundaries
The Python scraper must be designed with strict modular separation to prevent cross-layer contamination.

```text
scraper/
├── workers/        # Worker lifecycles (HTTP, Browser)
├── contracts/      # Typed schemas (Pydantic models for inputs/outputs)
├── adapters/       # Platform-specific orchestration
│   ├── facebook/
│   ├── instagram/
│   ├── threads/
│   └── x/
├── fetch/          # HTTP networking, retry logic, headers
├── browser/        # Playwright/Chromium context lifecycle
├── proxy/          # Proxy selection, rotation, and health scoring
├── parsers/        # Raw DOM/JSON to semantic fields extraction
├── normalizers/    # Platform semantic fields to Universal Schema
├── pagination/     # Collection loop, cursor management
├── diagnostics/    # Safe DOM snapshotting and metadata capture
├── errors/         # Structured error classification and exceptions
├── observability/  # Metrics, structured JSON logging, tracing
├── security/       # SSRF validation, secret sanitization
└── utils/          # General helpers
```
*Rule: Parsers must not depend on network fetchers; adapters orchestrate the flow between fetch, parse, and normalize.*

## 7. Worker Types
Two distinct worker classes process jobs independently from separate queues.

### HTTP Worker
The primary, default execution engine. It relies entirely on standard HTTP requests.
- High throughput, low overhead.
- Responsible for proxy assignment, payload fetching, parsing, and normalization.

### Browser Worker
The fallback engine (Playwright/Chromium). 
- Initial concurrency strictly capped at `1` per container/VPS.
- Used **only** when explicitly directed by `mode: "browser"`, or when `mode: "auto"` determines the target capability strictly requires browser rendering, or when a platform explicitly permits browser fallback.
- Never used for browser-first arbitrary crawling.

## 8. Laravel ↔ Python Job Contract
Laravel and Python communicate via internal execution payloads. Python operates on **Scrape Executions**, not customer Jobs.

- Laravel creates a `scrape_execution` record in PostgreSQL.
- Laravel pushes a JSON envelope to a Redis queue.
- Python consumes the envelope, fetches the full execution context if necessary, runs the job, and updates PostgreSQL.

## 9. Job Input Schema
The internal execution envelope payload structure:

```json
{
  "execution_id": "exec_01H...",
  "source_type": "api",
  "platform": "instagram",
  "operation": "profile_posts",
  "target": {
    "type": "username",
    "value": "example"
  },
  "options": {
    "limit": 50,
    "mode": "auto"
  },
  "parser_version": null,
  "proxy_policy": {
    "mode": "auto"
  },
  "diagnostics": {
    "enabled": false
  },
  "trace": {
    "request_id": "req_01H..."
  }
}
```
**Constraints:**
- Python trusts the `execution_id`, `platform`, `operation`, and `options`.
- Python MUST revalidate the `target.value` for SSRF and hostname safety regardless of upstream validation.
- Python NEVER receives Laravel `APP_KEY`, plaintext user API keys, admin session credentials, or unrelated tenant IDs.

## 10. Execution Context
Upon receiving a job, Python instantiates an `ExecutionContext`. This object holds the `request_id`, trace IDs, `execution_id`, logger instance, metrics aggregator, and the assigned proxy. This context is passed down through the modules, ensuring all logs and metrics are perfectly correlated.

## 11. Platform Adapter Contract
Adapters orchestrate scraping for a specific platform. All adapters implement a universal interface:

- `supports(operation) -> bool`
- `validate_target(target, options) -> bool`
- `build_request(...) -> HttpRequest`
- `fetch(...) -> HttpResponse`
- `parse(...) -> RawData`
- `normalize(...) -> UniversalSchema`
- `classify_response(HttpResponse) -> ErrorClassification`

Adapters do not share platform-specific bypass logic; they utilize the core `fetch` and `proxy` layers.

## 12. Operation Contract
Operations are capability-driven and defined by the platform.
- Common operations: `profile`, `profile_posts`, `post`, `search`, `hashtag`.
- If an operation is requested but unsupported by the adapter, execution stops immediately with `UNSUPPORTED_OPERATION`.

## 13. Target Contract
Target processing normalizes inputs for the fetcher.
- Python receives the target `{ "type": "username", "value": "example" }`.
- The platform adapter handles specific normalization (e.g., stripping `@` from usernames).
- The core security layer performs canonical URL generation, strict hostname verification (allowlist), redirect validation, and SSRF filtering before any network connection is established.

## 14. HTTP Fetch Layer
Responsible for all raw network I/O.
- Enforces HTTPS for all external targets.
- Enforces explicit connect and read timeouts (respecting the total execution timeout).
- Evaluates response size limits to prevent memory exhaustion.
- Enforces safe redirect handling (max redirects, re-validating each hop for SSRF).
- Honors `Retry-After` headers natively.
- Handles content-type validation and decompression.
- Captures safe response metadata: HTTP status, bytes received, duration, redirect count, and safe final URL.
- Does **not** inject stealth headers or spoof fingerprints (standard user-agent rotation is permitted only as basic HTTP configuration).

## 15. Browser Fallback Layer
Responsible for Playwright/Chromium lifecycle.
- Runs only in the designated Browser Worker.
- Uses strict isolated contexts (incognito) per execution.
- Contexts and pages are forcefully closed and cleaned up after every execution; no persistence.
- Captures necessary DOM diagnostics only.
- Does **not** implement CAPTCHA bypass, stealth plugins (e.g., puppeteer-extra-plugin-stealth), or hidden automation evasion.

## 16. Proxy Integration
Proxies ensure network reliability and regional egress.
- Selection relies on: Platform, Health state, Latency, Success rate, and Cooldown status.
- A proxy is only rotated upon retryable network failures (e.g., connection reset).
- **Forbidden:** Proxies must NEVER be rotated to bypass `CHALLENGE_PRESENT`, `AUTH_REQUIRED`, or `ACCESS_RESTRICTED`.

## 17. Parser Architecture
Strict separation exists: `Fetcher → Parser → Normalizer`.
- **Parser Responsibilities:** Consume raw HTTP/DOM responses, extract semantic fields (JSON or HTML structures), calculate required-field coverage, and output a structured intermediate result.
- **Prohibitions:** Parsers do not hit the network, do not calculate billing, do not manage tenant data, and do not make authorization decisions.

## 18. Parser Versioning
Every parser invocation uses an explicit version (aligned with the database).
- States: `candidate`, `active`, `previous`, `disabled`.
- Only one active parser per platform/operation combination.
- The `parser_version` string is permanently attached to every extracted item.
- Candidate parsers are NOT automatically promoted.

## 19. Normalizer Architecture
Normalizers map parser-specific output into the standard API Normalized Item Contract.
- Must preserve: `platform`, `content_type`, `external_id`, `canonical_url`, `author`, `text`, `published_at`, `media`, `metrics`, `platform_fields`, `collected_at`, `parser_version`.
- **Zero Semantics:** `0` indicates a confirmed zero. `null` indicates unavailable or unknown. Missing metrics must remain `null`.

## 20. Normalized Item Contract
Standard structures for nested objects.
**Author Contract:**
```json
{
  "external_id": null,
  "username": null,
  "display_name": null
}
```
Fields must be `null` if unavailable. Do not hallucinate or extrapolate values.

## 21. Pagination / Collection Loop
Generic safe loop implementation:
```text
Validate Execution → Resolve Adapter → Resolve Parser → Select Proxy 
→ Fetch → Parse → Normalize → Validate → Collect 
→ Determine Next Page/Cursor → Evaluate Stop Conditions → Repeat or Stop 
→ Return Execution Result
```
- Safeguards: Maximum pages bounded, cursor uniqueness enforced (no infinite loops), execution timeout strictly monitored.

## 22. Deduplication During Collection
**Execution-level deduplication:** Python ensures the same upstream item (identified by `external_id` or `canonical_url`) is not collected twice within a single execution loop.
**Customer/Job coalescing:** Python does NOT deduplicate across jobs. Laravel handles request fingerprinting and coalescing.

## 23. Stop Conditions
The collection loop terminates immediately if:
- Requested limit is reached.
- Next cursor/page is missing or duplicated.
- Max pages or global execution timeout is reached.
- Upstream rate limit or platform circuit breaker requires halting.
- `CHALLENGE_PRESENT`, `ACCESS_RESTRICTED`, or `AUTH_REQUIRED` is encountered.
- Cancellation signal is received.
- Unrecoverable parser failure or persistent network error occurs.

## 24. Retry Strategy
Retries apply **only** to transient failures (e.g., TCP connection reset, temporary DNS failure, safe 5xx errors, proxy connectivity issues).
- Bounded max attempts (e.g., 3).
- Exponential backoff with jitter.
- Absolute precedence to `Retry-After` headers.
- **Never** retry security/access classifications (`CHALLENGE_PRESENT`, `AUTH_REQUIRED`).

## 25. Error Classification
Python internally classifies errors before mapping to safe public outcomes:
- `NORMAL`
- `RATE_LIMITED`
- `ACCESS_RESTRICTED`
- `CHALLENGE_PRESENT`
- `AUTH_REQUIRED`
- `NETWORK_ERROR`
- `UPSTREAM_ERROR`
- `PARSING_FAILED`
- `PROXY_UNAVAILABLE`

Python maps these to execution outcomes. Laravel translates execution outcomes to safe public API errors (e.g., `SCRAPER_TIMEOUT`, `INTERNAL_ERROR`). Raw stack traces are never saved as public error messages.

## 26. Rate Limiting Behavior
Upon encountering HTTP 429:
- Read `Retry-After` if present.
- Classify as `RATE_LIMITED`.
- Signal a cooldown requirement to the control plane (Redis).
- Stop or backoff according to bounded policy. Do not spam requests.

## 27. Circuit / Cooldown Interaction
Circuit states (`CLOSED`, `OPEN`, `HALF_OPEN`) are managed by the control plane.
- Python reports success/failure signals to Redis (or via execution status).
- Python reads transient circuit state before fetching to avoid hammering degraded platforms.
- Python is not the durable owner of the circuit breaker rules.

## 28. Challenge / Authentication / Access Restriction Handling
- **`CHALLENGE_PRESENT`**: Stop collection immediately.
- **`AUTH_REQUIRED`**: Stop collection (unless an approved authenticated mode capability exists in the future).
- **`ACCESS_RESTRICTED`**: Stop collection (e.g., private profiles).
- **Forbidden:** Python MUST NOT solve CAPTCHAs, rotate proxies to bypass these blocks, bypass logins, spoof fingerprints, or inject stolen cookies.

## 29. Diagnostic Capture
Diagnostics capture safe context to aid debugging and AI parser recovery.
- Includes: HTTP status, safe final URL, fetch mode, parser version, masked proxy reference, timing, retry count, stop reason.
- May include a sanitized response snippet or reduced DOM snapshot.
- Never stores: API keys, raw cookies, passwords, or full raw HTML indiscriminately.

## 30. Parser Failure Recovery & Data Sanitization
Triggered by material coverage drop or structural failure (`PARSING_FAILED`).
- Captures a DOM snapshot.
- Uses a **DOM Snapshot Builder** to sanitize and reduce the DOM (stripping cookies, auth tokens, scripts, inline styles, embedded credentials, session data).
- Sends the reduced structural representation for analysis.

## 31. AI Parser Candidate Workflow
AI is used strictly for parser maintenance assistance.
- Triggers on failure or manual request.
- AI (OpenAI MVP) generates a *candidate* extraction rule (selector/regex).
- The candidate is validated via Python fixtures.
- An Admin must manually approve the candidate.
- AI NEVER automatically activates a production parser.
- AI failure degrades gracefully; it does not fail customer scraping beyond the initial parser break.

## 32. Redis Coordination
Redis provides transient state coordination only:
- Job queues (push/pop executions).
- Cancellation signal flags (pub/sub or key checks).
- Worker heartbeats.
- Temporary proxy/circuit cooldown states.
- Redis is NOT a durable source for customer results.

## 33. Worker Heartbeats
Workers emit periodic heartbeats to Redis containing safe metadata:
- Internal worker identifier, type (HTTP/Browser), status (idle/processing).
- Current `execution_id`.
- Last heartbeat timestamp.
- Available capacity/concurrency.
No secrets are included. Control plane uses this to detect stale or dead workers.

## 34. Cancellation Handling
- Laravel owns customer Job cancellation.
- Python listens for execution-level cancellation signals in Redis.
- A shared execution (supporting multiple coalesced jobs) is only cancelled if Laravel determines no remaining jobs depend on it and issues the execution-level kill signal.
- Python terminates gracefully between pagination loops upon receiving the signal.

## 35. Timeouts & Resource Limits
- Executions must have a hard global timeout.
- Browser contexts have strict memory and duration bounds.
- Container limits (RAM/CPU) are enforced via Docker. The initial target is a 4 GB VPS, mandating low-concurrency lightweight HTTP workers and maximum 1 Browser worker.
- Infinite loops are prevented via explicit bounds on pagination and response body sizes.

## 36. Logging & Observability
**Logging:**
- Structured JSON format.
- Fields: timestamp, level, `execution_id`, `request_id`, platform, operation, worker_type, mode, error_classification.
- **Forbidden:** Never log API keys, proxy passwords, cookies, session tokens, authorization headers, or Laravel `APP_KEY`.

**Metrics (Observability):**
- Count requests, successes, partials, failures.
- Measure latency (fetch, parse, normalize).
- Track error classifications, proxy success rates, and queue depth.

## 37. Security Boundaries & SSRF
- **SSRF Safety:** Python enforces defense-in-depth target validation. Blocks loopback (127.0.0.0/8), RFC1918 (10.x, 192.168.x, 172.16.x), link-local, cloud metadata (169.254.169.254), and Docker internal IPs. Redirects are re-validated.
- **Secret Handling:** Python runs non-root with minimal permissions. Proxy credentials are only kept in memory during fetch and masked in all outputs/diagnostics. Contexts are fully destroyed after execution.

## 38. Partial Success Contract
An execution becomes `partial` if some items are successfully normalized but the collection stops before the requested limit due to a safe stop condition (timeout, rate limit, network error).
- Result includes: successful item count, requested item count, and a safe stop reason.
- Valid records are retained and saved, never discarded merely because subsequent pagination failed.

## 39. Cache & Coalescing Interaction
Python operates exclusively on `scrape_executions`.
- Laravel handles request fingerprinting to determine if a new execution is needed or if jobs can be coalesced.
- Python processes the execution once. It does not need tenant identities.
- Laravel attributes the saved output of the single execution to all waiting Jobs and applies the standard Quota Boundary (e.g., 50 records = 50 quota) universally.

## 40. Result Output Contract (Python → Laravel)
Python produces a canonical execution result object.
```json
{
  "execution_id": "exec_01H...",
  "status": "completed",
  "platform": "instagram",
  "operation": "profile_posts",
  "mode_used": "http",
  "parser_version": "instagram-profile-posts-v3",
  "items": [{...}],
  "summary": {
    "requested": 50,
    "collected": 50,
    "valid": 50,
    "invalid": 0
  },
  "diagnostic": {
    "duration_ms": 1200,
    "attempts": 1,
    "stop_reason": "limit_reached"
  },
  "error": null
}
```
No raw secrets, stack traces, or Laravel DB IDs are included.

- Secret-redaction and logging safety tests.

## 42. Fixture Strategy & Controlled Live Validation
- Parsers must be tested against offline, sanitized HTML/JSON fixtures (successful, empty, missing fields, rate-limited, challenge).
- Fixtures must never contain exposed real credentials or private unauthorized data.
- **Controlled Live Validation:** Candidate parsers require fixture validation, normalized schema validation, failure classification review, and manual Admin approval before activation. Uncontrolled live scraping is prohibited.
