# Google Stitch Master Design Prompt
**Project:** Scraping & Data Collection as a Service
**Objective:** Design the COMPLETE application. Design every single screen specified in the registry.

You are tasked with designing all UI screens, states, and flows for this Enterprise SaaS application based strictly on the locked product requirements.

---

## 1. VISUAL DIRECTION: DARK / BLACK ENTERPRISE SAAS
The PRIMARY and DEFAULT visual theme for this product is a professional DARK / BLACK THEME.


### Semantic Design Tokens:
- **App Background**: `#090909`
- **Sidebar / Navigation**: `#0D0D0D`
- **Primary Surface**: `#121212`
- **Elevated Surface**: `#181818`
- **Input / Table Surface**: `#151515`
- **Border / Divider**: `#262626`
- **Primary Text**: `#F5F5F5`
- **Secondary Text**: `#A3A3A3`
- **Muted Text**: `#737373`
- **Accent Color**: Use one restrained primary accent color consistently for primary CTA, active navigation, links, focus, selected states, and important interactive emphasis.

### Styling Constraints:
- **Tone**: Professional, enterprise SaaS, operational, modern, data-oriented, premium but restrained, highly readable.
- **Hierarchy**: Preserve hierarchy between App background, Navigation, Cards, Tables, Forms, Modals, Dropdowns, and Elevated panels. Use subtle contrast between dark surfaces.
- **Avoid**: Neon, glow, excessive gradient, excessive glassmorphism, gaming dashboard appearance, crypto dashboard appearance, excessive border, excessive shadow, oversized cards. Do NOT make every surface pure black.
- **Status Colors**: Success (Normal), Warning (Limited), Error (Danger), Information, Maintenance, Unavailable. NEVER communicate status using color alone (always color + icon + text).
- **Charts**: Must be designed for dark surfaces (strong label contrast, readable axes, restrained grid lines, distinguishable series, accessible legends, useful tooltips).

---

## 2. RESPONSIVE DESIGN (FIRST-CLASS MOBILE UX)
Mobile is a first-class design requirement. Design important screens for **375px, 768px, 1024px, and 1440px**.
**Do NOT simply scale desktop down.**

### Rules:
- **NO Horizontal Page Overflow**: There must NEVER be horizontal page overflow.
- **Wide Tables**:
  1. Prioritize important columns.
  2. Hide secondary columns.
  3. Use expandable rows.
  4. Transform to cards on mobile when appropriate.
  5. Use controlled internal table scrolling only as a last resort.
- **Mobile Adjustments**:
  - Compact topbar, navigation drawer, or suitable mobile navigation.
  - Stacked KPI cards (horizontally scrollable KPI groups only when useful).
  - Filters may use bottom sheets.
  - Forms become stacked/single-column.
  - Actions remain touch-friendly.
  - Sticky primary action where useful.
  - Dense operational data must remain understandable.

---

## 3. CRUD UX STANDARD & UI STATES
Respect the locked CRUD UX rules for important records:
`List → Detail → Dedicated Create/Edit Page → Confirmation → Processing → Toast → Detail/List`

- **No Edit Modals**: Do not make Edit Modal the default for important records. Quick Edit Modal is ONLY allowed for simple low-risk fields.
- **Required Mutation States**: Every mutation must have loading, duplicate-action prevention, confirmation according to risk, success toast, and error toast.
- **Data-driven Screen States**: Every screen must have meaningful states:
  - **Loading**: Application shell renders first. No generic spinners. Use screen-specific skeletons designed for dark surfaces (subtle dark tonal differences, no bright flashing).
  - **Skeleton**: Contextual to the data structure.
  - **Loaded**: The primary data view.
  - **Empty**: Icon + concise text + CTA. Do not use decorative illustrations in dense operational interfaces.
  - **Error**: State with clear error details and retry actions.
  - **Partial/Degraded**: Local degradation (warning inside the affected card/screen) vs. Global degradation (App-shell warning banner).

---

## 4. SECURITY & DATA PRIVACY
Never expose plaintext secrets:
- Passwords, OTP, API keys (after initial creation), social account credentials, cookies, session credentials, proxy passwords, Evolution API tokens, Telegram bot tokens, SMTP passwords, AI provider keys, Object Storage secrets.
- **Use masking**: E.g., `Configured`, `••••••••••`, or `Replace Credential`.

---

## 5. CRITICAL ACTION RISK LEVELS
- **LOW**: Normal action, toast.
- **MEDIUM**: Confirmation modal.
- **HIGH**: Danger confirmation, reason required where applicable.
- **CRITICAL**: Typed confirmation, re-authentication/MFA state, reason required, audit indication.

---

## 6. ROLE SEPARATION & PRODUCT DISTINCTIONS
Maintain one coherent design language across all domains, but strictly enforce these boundaries:
- **Customer Roles**: Customer Owner, Developer, Analyst, Viewer.
- **Internal Roles**: Owner, Admin, Operator / Support, Finance, Auditor / Security.
- **Strict Isolation**: Customer and internal roles must NOT be mixed. Internal AI must NEVER be presented to ordinary customer users. Finance internal-cost information must NEVER be exposed to customer roles unless explicitly authorized.

### Explicit Visual Distinctions Required:
- **Harga ke User vs. Biaya Sebenarnya ke Sistem**: Customer sees pricing/credit/usage. Finance sees actual system cost/profit/margin.
- **Run vs. Task**
- **Account Pool vs. Proxy Pool**
- **Error vs. Incident**
- **Degraded vs. Maintenance vs. Unavailable**
- **Generated Export vs. Canonical Scraping Data**
- **WhatsApp Multi-instance**: Explicit UI support for multiple WA instances/pools via Evolution API.
- **Internal AI**: Strictly read-only v1, purely internal.
